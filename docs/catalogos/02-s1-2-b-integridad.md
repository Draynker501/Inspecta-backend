# S1.2-B — Integridad de códigos de planta

Estado: **validación de integridad SQLite/MariaDB aislada; CAT-01 aún no lista para publicación**. Se conserva la validación previa por organización que incluye plantas con soft delete y el índice existente como garantía final.

En SQLite, la colisión real observada después de la validación produjo SQLSTATE `23000`, código PDO `19` y `UNIQUE constraint failed: plants.organization_id, plants.code`. La captura se limita al insert de planta, al driver SQLite y a esa combinación exacta; se convierte en `validation_failed` sin incluir SQL. Otros errores se propagan. La prueba fuerza una colisión real dentro de la misma transacción después de la validación; no demuestra concurrencia entre conexiones.

En un contenedor **temporal autorizado** MariaDB 11.8.9, con base `inspecta_s12b_test`, puerto ligado solo a localhost y datos en tmpfs, se verificó explícitamente `APP_ENV=testing`, destino y `TestDatabaseGuard` antes de migrar. La columna `plants.code` usa `utf8mb4_unicode_ci` (la colación por defecto de la base temporal puede diferir). El índice consultado tiene las columnas `(organization_id, code)` en ese orden. Pruebas SQL reales: colisión del índice → `UniqueConstraintViolationException`, SQLSTATE `23000`, código `1062`, clave `plants_org_code_unique`; PRIMARY → también `23000/1062`, pero clave `PRIMARY`; FK → `QueryException`, `23000/1452`. El detector de MariaDB exige simultáneamente driver, SQLSTATE, código y nombre exacto de clave al final del diagnóstico. Cualquier otro error se propaga.

La prueba HTTP fuerza una colisión real posterior a la validación en la misma transacción (ambos motores), pero no simula dos conexiones. Un experimento independiente con **dos conexiones PDO** dejó la primera inserción sin confirmar mientras la segunda esperaba; tras confirmar la primera, la segunda falló con `23000/1062`, clave `plants_org_code_unique`, y quedó una sola fila. Si no se confirma y se supera el tiempo de espera, se observó `HY000/1205`: **no** es duplicado y nunca debe traducirse a 422. Los experimentos de concurrencia utilizaron exclusivamente la base temporal; no son una prueba HTTP de dos peticiones simultáneas ni demuestran ausencia de deadlocks.

En la colación efectiva de la columna temporal, las comparaciones SQL equiparan `pl-1` y `PL-1`, `PL-1` y `PL-1 `, y `A` y `Á`. La API nueva admite únicamente códigos canónicos ASCII, pero datos históricos con acentos pueden colisionar: auditar los datos del destino antes de desplegar. La suite POST MariaDB incluye el caso de soft delete, otro tenant y rollback de auditoría.

La colación efectiva y los datos de **entornos existentes** no se consultaron. Su verificación de solo lectura y la revisión de consumidores panel/PWA siguen siendo gates previos a publicación/despliegue. OpenAPI permanece sin modificar y la prueba de correspondencia falla porque el POST implementado sigue marcado `planned`. La prueba de concurrencia SQLite entre conexiones independientes no puede equivaler a la de MariaDB en `:memory:` sin un diseño de base compartida aislada; no inferir esa cobertura.
