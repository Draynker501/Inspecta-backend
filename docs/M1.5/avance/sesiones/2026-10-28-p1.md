## 3. Defectos encontrados y cómo se resolvieron (REPORTADO)

| Defecto | Síntoma | Resolución |
|---------|---------|------------|
| Hook de doble escritura reactivaba membresías revocadas en cualquier guardado | Guardar un User sin cambiar `organization_id` (solo nombre) pasaba la membresía de revoked a active | El hook `booted()` ahora filtra con `wasRecentlyCreated || wasChanged('organization_id')`; `ensureMembership()` usa `firstOrCreate` y **nunca** modifica `status` ni `revoked_at` de una membresía existente. La reactivación será operación explícita de P3. |
| Seeders no generaban membresías; el backfill-migration corría antes de sembrar | Tras `migrate:fresh --seed`, usuarios sin membresía porque `UserSeeder` usa `WithoutModelEvents` (no dispara el hook `saved`) y el backfill-migration se ejecuta sobre BD vacía | `UserSeeder::run()` invoca `MembershipBackfill::run()` al final. Se mantiene `WithoutModelEvents`. El backfill usa `DB::table`, idempotente. |
| Prueba esperaba reactivación automática | `test_reactiva_membresia_revocada_al_cambiar_organization_id` esperaba `STATUS_ACTIVE` tras cambiar `organization_id` a una org con membresía revocada | Prueba renombrada a `test_no_reactiva_membresia_revocada_al_cambiar_organization_id`; ahora espera `STATUS_REVOKED` y `revoked_at` no nulo. |

## 4. Verificación en MariaDB 11.8.9 (REPORTADO, no reverificada hoy)

Realizada en sesión anterior con contenedor `inspecta-mariadb-verif` (imagen `mariadb:11.8`, puerto 127.0.0.1:33061, base `inspecta_verif`), luego destruido.

- `SELECT VERSION()` → `11.8.9-MariaDB-ubu2404`
- `migrate:fresh --seed` con variables en línea: 40 migraciones en `Ran`, seeders sin error.
- Conteo: `users = 3`, `organization_memberships = 3`, usuarios sin membresía = 0, membresías con organización distinta a la del user = 0.
- Backfill idempotente en dos ejecuciones (`migrate:rollback --step=1` + `DELETE` + `migrate`, repetido dos veces): mismos conteos, 0 duplicadas.
- Rollback de los 3 pasos (`migrate:rollback --step=3`): `organization_memberships` y `organizations.type` eliminados; `users.organization_id` intacto. Luego `migrate` restauró las 40 migraciones.
- Tinker: revocar membresía con SQL + guardar User cambiando solo el nombre → sigue `revoked` (no se reactiva). Cambiar `organization_id` → crea membresía nueva y conserva la anterior (2 membresías). Cambiar `organization_id` de vuelta a la org con membresía revocada → sigue `revoked`.
- Segunda `migrate:fresh --seed`: mismas cifras (idempotente).
- Limpieza: `docker stop` + `docker rm -v`; contenedor y volumen eliminados.

## 5. Decisiones de diseño tomadas durante la sesión

| Decisión | Descripción |
|----------|-------------|
| Hook solo actúa al crear o cambiar `organization_id` | `booted()` filtra con `wasRecentlyCreated || wasChanged('organization_id')`. Cualquier otro guardado no hace nada. |
| `ensureMembership()` nunca modifica membresía existente | Usa `firstOrCreate`; si existe (activa o revocada), no la toca. La reactivación es operación explícita de P3. |
| `MembershipBackfill` usa `DB::table` | No depende de `OrganizationScope` ni `BelongsToOrganization`. Idempotente por `(user_id, organization_id)`. |
| `status` como string (`'active'`/`'revoked'`) | No boolean, por coherencia con posibles valores futuros y con `revoked_at` como timestamp. |
| `User` sigue con `BelongsToOrganization` y `organization_id` en `#[Fillable]` | Se retiran en P3, no en P1. |
| No se creó la organización operadora (INSPECTA-OP) | Se crea en P4. `organizations.type` tiene default `'client'`. |
| `down()` del backfill-migration sin operación | La tabla `organization_memberships` se elimina con el `down()` del paso 1.1. |
